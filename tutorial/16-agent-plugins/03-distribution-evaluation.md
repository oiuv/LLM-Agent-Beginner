# 03：分发、市场与评测

## 市场与包格式分别解决问题

| 分发对象 | 用户主要寻找什么 |
|---|---|
| Skill 目录或市场 | 某类任务的方法与流程 |
| MCP 服务目录或市场 | 可连接的工具、资源与服务 |
| Plugin 市场 | 已组合好的能力包 |

同一市场可以提供多种对象。市场负责展示、搜索、获取或审核的方式；插件规范负责目录与组件契约。不能把某个市场的安装命令、签名或评分字段写成通用 Manifest 标准。安装、启用、更新和分发界面不在可移植格式的定义范围内。[官方包边界说明](https://agent-plugins.org/plugin-authors/build-an-agent-plugin#package-boundaries)

选择真实客户端时，先查 [兼容客户端列表](https://agent-plugins.org/compatible-clients)，再核对该客户端的组件、传输和扩展支持。市场中出现一个插件，不等于任意 Agent 都能原样加载。

## 从开发到交付

本教程建议采用以下流程；这些步骤是工程实践，不是新增的包格式：

1. 在标准目录中编写 Skill 和连接配置。
2. 执行静态检查，确认包内引用完整，没有真实用户数据或凭证。
3. 在目标宿主查看实际发现的 Skill 和工具。
4. 用成功、信息不足、工具不可用和取消用例检查执行轨迹。
5. 固定依赖与内容摘要，记录测试过的客户端版本。
6. 再按目标分发渠道提交插件，升级前重新检查权限和行为变化。

向插件内增加脚本、外部域名或写操作，可能扩大运行权限。宿主应展示实际变化并沿用授权策略；安装来源可信不意味着运行时动作全部获准。详见 [安全与评测](../13-safety-evaluation/README.md)。

## 版本与用户状态

$schema 选择规范契约，version 表示插件发布版本。两个 JSON 配置引用的规范版本要一致；发布版本建议使用语义化版本。[规范版本规则](https://agent-plugins.org/specification#10-versioning)

本教程的宿主设计建议：

- 运行中的任务固定所用内容，不在半途切换 Skill。
- 更新只替换发布内容，保留并按需迁移运行数据。
- 回滚插件后，检查数据仍能被读取；回滚代码不能撤销已发送的消息。
- 卸载先停止相关后台任务、关闭连接，再按用户的数据保留选择处理状态。

## 学习导师的验收

| 用例 | 要观察的行为 |
|---|---|
| 给出题目和错误作答过程 | 诊断引用实际步骤，区分事实与推断 |
| 只有题目，没有作答 | 请求补充，不编造学生错误 |
| 请求逐步练习 | 每次给出有限提示并等待新尝试 |
| 简单概念问答 | 不强行启动完整诊断流程 |
| MCP 验算不可用 | 如实说明工具不可用，不声称已调用 |
| 用户取消或拒绝写入 | 停止相应动作，不靠换工具绕过 |
| 重复安装或更新 | 不复制用户记忆，不创建重复提醒 |

这些是需要在目标宿主或模型适配器中执行的行为用例；静态检查不会自动证明它们通过。教学效果仍需要独立评测，不能用“插件成功加载”代替。

## 当前检查工具的边界

npm run check:plugins 是仓库内样例的作者检查器：使用本地官方 Schema，检查标准 JSON、Skill 元数据和文件真实路径。它不会安装插件、加载客户端扩展、连接 MCP 或调用模型，也不是通用一致性认证工具。

MCP 的单独运行方法见 [样例说明](../../examples/learning-coach-plugin/README.md)。实际接入宿主后，还要记录客户端版本、发现结果、调用结果与失败轨迹，才能声称该集成已验证。
