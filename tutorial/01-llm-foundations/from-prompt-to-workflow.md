# 从一次提示到可验证工作流

贯穿任务：根据测验证据，安排一份 **30 分钟、覆盖薄弱知识点、使用已有资源** 的学习计划。每次只为一个已出现的问题增加机制，不把模式当作必须收集的组件。

## 1. 单次提示：先建立基线

输入测验摘要和可用时间，让模型直接生成计划。问题是“读起来合理”仍可能安排 60 分钟、漏掉知识点，或引用不存在的练习。

先把验收条件写成数据：目标知识点、可用分钟数、资源目录。对自然语言质量和结构约束分别评测，不用更长的提示词替代检查。

## 2. 提示链：让上一步的产出可以检查

将任务拆成“读取证据 → 确定练习目标 → 收集资源 → 生成计划 → 验收”。稳定步骤由代码执行，需要开放判断的步骤才调用模型。

每个节点产生结构化输出。诊断失败就停在诊断节点，不继续编造后续计划。这里的链是数据依赖，节点不一定都是 LLM 调用。

## 3. 路由：缺少信息时换路径

| 当前证据 | 路径 |
|---|---|
| 没有测验证据或可用时间 | 请求补充输入 |
| 有明确薄弱点 | 进入资源与计划流程 |
| 当前证据没有练习目标 | 确认新目标或安排诊断 |
| 必需资源不可用 | 报告缺口，选择替代资源或暂停 |

规则足以判断的分支用规则。只有意图不确定时才考虑模型分类，并为低置信度保留澄清路径。

## 4. 并行：等待独立数据，而不是提前执行依赖

多个知识点的只读资源查询可以并行；生成计划必须等待所需资源到齐。使用 Promise.allSettled 保留每个分支的结果和失败，必需输入失败不能被成功分支掩盖。

并行减少独立等待时间，也可能提高峰值请求量。生产环境还需并发上限、超时和取消；示例使用少量本地查询。

## 5. 反馈修正：把失败原因交回模型

检查计划是否覆盖目标、总时长是否超限、resourceId 是否属于对应知识点。检查失败时，把具体问题与候选答案交回模型；重新生成后仍执行同一验收器。

最多 3 次模型决策，避免反思无限循环。校验通过只说明交付约束满足，不能证明练习讲解正确、难度合适或学生已经掌握。

## 6. 动态规划：已有步骤无法覆盖变化时再引入

学生临时改为 15 分钟、资源失效或发现新误区时，才需要修改目标或计划。记录计划版本、变化原因、已完成动作与剩余预算，再选择下一步。

示例实现到固定工作流与有限修正；动态 Plan、跨进程恢复和持续教学是 [阶段 4](../04-planning-workflow/README.md)、[阶段 9](../09-scheduling/README.md) 的实现练习。一次计划通过验收并不意味着长期目标完成。

## 运行与观察

在仓库根目录运行：

~~~sh
npm run tutorial:patterns
npm test
~~~

预期看到：

- 60 分钟候选计划验收失败；
- 修正为 20 分钟后 completed，模型调用 2 次；
- 验收事件依次为 error、ok；
- 缺少证据时返回 needs_input；
- 工具预算为 0 时，调用提案在执行前被拒绝；
- 同时就绪的任务先领取 review-before-exam。

代码：[工作流与验收器](../../examples/learning-agent-runtime/src/study-workflow.ts)、[实验入口](../../examples/learning-agent-runtime/src/patterns.ts)、[回归测试](../../examples/learning-agent-runtime/src/patterns.test.ts)。

这些实验使用 ScriptedModel，证明运行时能检查、反馈和停止。要证明某种模式改善真实模型，需要固定任务集，对比任务成功率、调用次数、延迟和费用；不要把脚本预设的第二个答案算作模型学习效果。

## 练习

1. 增加一个知识点，并让其中一个资源查询失败：计划模型应保持零调用。
2. 让所有候选答案超时长：到达步数上限后必须 failed。
3. 学生将时间改成 15 分钟：明确哪些状态失效，哪些已完成动作保留。
