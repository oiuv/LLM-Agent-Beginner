# 用运行行为评估框架与 SDK

先明确需要解决的问题，再选择框架。框架可减少适配、状态图或追踪工作，但不会自动提供业务正确性、最小权限或可靠的持久化。

## 用同一任务比较

将阶段 3 的“查询知识点 → 根据结果回答”接入一个候选 SDK，保持输入、工具、权限与验收器不变，再观察：

| 能力 | 需要的证据 |
|---|---|
| 模型适配 | 工具调用 ID 与结果能对应，拒绝和取消不丢失 |
| 状态与恢复 | 杀进程后恢复时不重复已提交副作用 |
| 人工介入 | 审批绑定具体参数，恢复时重新检查权限 |
| 编排 | 并发、失败汇合、预算与停止条件可配置 |
| 追踪 | 能定位模型、工具、策略与验收失败 |
| 可替换性 | 核心领域状态不依赖单一厂商消息对象 |

## 待实现观察实验

1. 记录所用 SDK、模型和依赖版本，按其官方文档创建独立适配器。
2. 跑正常调用、工具错误、预算耗尽与取消四条轨迹。
3. 对比本项目确定性测试中的状态和事件。
4. 若考察 handoff，再验证委派权限与结果汇总，见 [阶段 11](../11-multi-agent/README.md)。
5. 记录框架实际提供的能力，以及仍需自行实现的部分。

不要引用作者电脑上的其他检出目录作为教程前置；实验代码、依赖与命令都应能从仓库复现。SDK 更新后重跑行为实验，避免用容易过时的框架排名代替选择依据。
